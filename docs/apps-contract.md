# Pushed-app CLI contract (ticket 03)

`awtrix apps create NAME (--payload JSON | --file PATH) [--raw]` and `awtrix apps update NAME (--payload JSON | --file PATH) [--raw]` both send the required JSON object via `PUT /api/v1/apps/pushed/{name}`. `--file` reads UTF-8 JSON and supports payloads too large for an OS argument vector. This route is an upsert: it creates when absent and replaces when present. The command labels do not establish create-only behavior or require that an app already exists. `awtrix apps delete NAME` sends `DELETE /api/v1/apps/{name}`. Names match `[A-Za-z0-9_-]{1,32}`.

The default validator rejects unknown keys; `--raw` explicitly opts into forwarding unknown device-specific fields without local type checks. The payload must be a non-empty JSON object. The local top-level type table covers all 35 official pushed-app keys shared by ESP32, ESP32-S3 and TC002; nested display structures are checked where their schemas are bounded (scroll and positioned icons), with device validation remaining authoritative for colors, drawing details and live capabilities. Timing fields use integer milliseconds. `durationMs <= 0` uses the device app duration; `lifetimeMs <= 0` disables expiration; `lifetimeExpiry` is `remove` or `mark`.

Request-body limits differ by actual platform: ESP32 and ESP32-S3 allow 8192 bytes; TC002 allows 2 MiB. Payloads at or below 8192 bytes do not require identity preflight. For larger serialized request bodies the CLI reads `/api/v1/device` before any mutation, maps only documented `boardType`/`soc` identities, and selects the matching limit. Unknown identity fails closed with an incompatibility error; it is not assumed to be TC002. A body exceeding the identified variant's limit is rejected locally before PUT. This avoids an ESP32-sized limit rejecting valid larger TC002 bodies while avoiding unsafe guesses. All three limits are from the variant-specific official Limits pages and apply to the actual pushed-app HTTP JSON request.

The API allows at most 50 resident pushed apps; replacing a name does not consume a slot. The client does not pre-query inventory/capacity, so server `422` payload validation and `507` storage/capacity responses are authoritative.

Successful mutation output reports `accepted: true` and `visibility: "unknown"`; HTTP acceptance is not evidence that the app is currently visible. Pushed apps reside in RAM, may expire by `lifetimeMs` (`lifetimeExpiry` is `remove` or `mark`), and are lost on reboot. They are distinct from persistent Berry scripts. HTTP 413/422/507 failures use shared API errors and do not disclose raw response bodies.

The command descriptions and `src/apps.rs` field-kind table are the behavior-adjacent schema contract. `--raw` does not change the payload-object, byte-limit, or route requirements; it bypasses local per-key recognition/type validation for explicitly forwarded extension keys.

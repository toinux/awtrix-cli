# Initial CLI contracts (ticket 01)

The command tree is deliberately domain-oriented (`device identity|state|capabilities|diagnose`); later slices should add sibling domains rather than place every operation at the root. `--target` (or `AWTRIX_URL`) is a required HTTP base URL. Optional `--username`/`--password` (or corresponding environment variables) enable Basic authentication. Requests have a finite `--timeout` in milliseconds (default 3000).

Machine output is compact JSON when `--json` is selected, independent of TTY detection. `--fields a,b` selects known top-level result fields; an unknown field is an argument error. Successful results go to stdout. Under `--json`, structured failures go to stdout as `{"error":{"code":"STABLE_CODE","message":"..."}}`, while a concise diagnostic also goes to stderr. CLI parse failures additionally emit clap's usage diagnostic to stderr. Exit codes: 0 success, 1 transport/general, 2 CLI/field selection, 3 authentication, 4 timeout, 5 HTTP, 6 incompatible device. Never include credentials or raw server response bodies in errors.

Device routes are the official AWTRIX NG `GET /api/v1/device`, `/api/v1/version`, `/api/v1/capabilities`, and `/api/v1/system` routes. Current identity uses `boardType` and `soc` from `/api/v1/device`: `awtrixng` + `esp32` means ESP32, `awtrixng` + `esp32s3` means ESP32-S3, and `tc002` means TC002. Other strings do not imply a variant. Identity and diagnosis require device state; no unrelated `/system` request is made. Offline `describe [topic]` advertises the ESP32 reference; supplying `--target` explicitly refines it with connected capabilities and propagates request failures. Capability names returned by the target are authoritative; no variant alone implies support.

Verified OpenAPI sources (retrieved 2026-10-07):

- https://blueforcer.github.io/awtrix-ng/esp32/api/openapi.yaml
- https://blueforcer.github.io/awtrix-ng/esp32-s3/api/openapi.yaml
- https://blueforcer.github.io/awtrix-ng/tc002/api/openapi.yaml

## Berry script source (ticket 07)

`script get NAME` sends `GET /api/v1/apps/script/{name}` and writes the `text/plain` source exactly to stdout in human mode, or as `{"source":"..."}` under `--json`, without an imposed JSON-body limit. `NAME` matches `[A-Za-z0-9_-]{1,32}`. `script deploy NAME (--source TEXT | --file PATH)` reads a non-empty UTF-8 source.

By default deploy requires `GET /api/v1/capabilities` to advertise `scriptUpdates: true`, and requires the caller's original `--expected-source TEXT` or explicit `--create`. The CLI does not refresh that reference immediately before writing. It uses atomic `PUT /api/v1/apps/script-update/{name}` with JSON `{ "expected_source": <string|null>, "source": <string> }`; null means create-only. HTTP 409 is `CONFLICT` (exit 1) and leaves remote source unchanged. Missing capability aborts before write (`PROTECTION_UNAVAILABLE`, exit 6); it never emulates atomicity with GET-then-PUT. `--force` explicitly selects raw `PUT /api/v1/apps/script/{name}` and reports the weaker guarantee; it is not a fallback.

Both routes are confirmed in official ESP32, ESP32-S3 and TC002 OpenAPI 3.1.0 definitions (retrieved 2026-10-07). Conditional update restores old source on compile/setup failure, not later runtime errors. HTTP 200 with non-null `error` is `BERRY_ERROR` (exit 1): saved source is not equivalent to successful execution. The CLI additionally reads `/api/v1/system` and `/api/v1/apps`; only explicit `scriptingEnabled:true` plus the named `origin:"script"`, `enabled:true` app with `error:null` yields `start_verified:true`. If verification is missing, disabled or inconclusive, it returns saved source with `start_verified:false`, `execution_state:"unknown"`. Forced raw PUT always reports execution unknown because that route does not establish start success. A timeout/transport interruption of a write has unknown outcome. AWTRIX's atomic update restores old source on compile/setup failure; later runtime errors are outside that rollback promise. Source uses the dedicated raw/text route and is never bounded by JSON request limits.

All three sources identify themselves as AWTRIX NG HTTP API OpenAPI 3.1.0 and define `DeviceState` identity constants: ESP32 has `boardType: awtrixng` / `soc: esp32`, ESP32-S3 has `boardType: awtrixng` / `soc: esp32s3`, and TC002 has `boardType: tc002`. They document the routes above and HTTP 401 for authenticated operations. Firmware versions and platform identity come from the live target, not a hardcoded compatibility claim. Unknown/unidentifiable hardware is reported as `unknown`.

## Screen capture (ticket 10)

`screen capture --output PATH` requests `GET /api/v1/display/screen` (the framebuffer route present in the official ESP32, ESP32-S3 and TC002 OpenAPI definitions). Its JSON object contains positive `width` and `height`, and `pixels` contains exactly width × height row-major unsigned decimal integers. Each integer is packed `0xRRGGBB`, not three channel values; the CLI writes an 8-bit RGB PNG. Current documented defaults are 32×8, but the command uses the response dimensions (for example 52×16) and caps input to 4,194,304 pixels. The response is also byte-bounded to ten bytes per allowed pixel plus 4096 bytes overhead; a known or streamed over-limit response is `RESPONSE_TOO_LARGE` before unbounded allocation. Invalid/truncated JSON, invalid/overflowing dimensions, a mismatched pixel count, or a pixel outside `0..=0xFFFFFF` is `INVALID_RESPONSE`. The compact result contains only `path`, `format`, `width` and `height`; local PNG failures are `FILE_WRITE`. Encoding completes before creating a sibling temporary file, which is flushed and persisted through `tempfile::NamedTempFile::persist` to replace the destination using its documented atomic replacement behavior on supported platforms. Any failure before persistence leaves the prior destination unchanged. A framebuffer is not deterministic frame synchronization and does not include physical brightness or panel color corrections.

Official contracts checked 2026-10-07: [ESP32 OpenAPI](https://blueforcer.github.io/awtrix-ng/esp32/api/openapi.yaml), [ESP32-S3 OpenAPI](https://blueforcer.github.io/awtrix-ng/esp32-s3/api/openapi.yaml), [TC002 OpenAPI](https://blueforcer.github.io/awtrix-ng/tc002/api/openapi.yaml), and [HTTP API framebuffer reference](https://blueforcer.github.io/awtrix-ng/reference/http).

## Ticket 02: personal profiles and target selection

`awtrix profile add NAME --target URL [--username USER] [--password PASS]`, `update NAME --target URL [--username USER] [--password PASS]`, `list`, `show NAME`, `set-default NAME`, and `delete NAME` manage profiles in the personal JSON config. `AWTRIX_CONFIG` overrides its path. Otherwise Windows uses `%APPDATA%/awtrix/config.json`, falling back to `%USERPROFILE%/AppData/Roaming/awtrix/config.json`; macOS and Linux use `$HOME/.config/awtrix/config.json`. If these variables are unavailable, configuration fails explicitly rather than using a shared temporary directory. Profile listing/show never return credential values; Unix config files are mode 0600. Selection precedence is explicit `--target`, `AWTRIX_URL`, explicit `--profile`/`AWTRIX_PROFILE`, then the configured default profile. A project reference slot is intentionally between environment and default and will be connected in ticket 13. `device diagnose` returns `target` and `target_origin` (`command-line`, `environment`, `profile`, or `default-profile`). Explicit and environment credentials (`--username`/`AWTRIX_USERNAME`, `--password`/`AWTRIX_PASSWORD`) override credentials in the selected profile; all descriptions omit credential values. `describe "profile add|update|list|show|set-default|delete"` returns operation-specific parameters, output field names, and examples.

## Ticket 11: bounded script verification

`script verify NAME [--duration-secs N] [--interval-ms N] [--after CURSOR] [--capture PATH]` verifies an existing script without deploying it. `script deploy ... [--verify-secs N]` performs the existing conflict-protected deployment first, then includes a verification report; it does not weaken `--expected-source`, `--create`, or `--force` rules. The observation duration is 1..3600 seconds and includes HTTP requests; each request timeout is clamped to remaining time. `observed_window.complete` is true only after the full requested duration elapses; `elapsed_ms` and `early_termination_reason` explain short observations. With capture requested, polling stops early enough to reserve a bounded portion of the same deadline (at most two seconds, one quarter of the window) for framebuffer HTTP and PNG persistence; if no time remains, capture is reported unavailable rather than extending the deadline. The command checks `/api/v1/system` and `/api/v1/apps` before observation; globally disabled scripting, an absent/disabled script, runtime Berry errors, and initial state/log collection failures return non-zero with a JSON report on stdout and diagnostic on stderr. During observation it polls `/api/v1/logs?after=<cursor>` and rechecks that the named app remains an enabled script, retaining the returned `next` cursor. Collection failure is included in `not_available`; log history is capped at 34 and `exhaustive:false`. `source_saved` is `not_requested` for verification-only, while deploy-then-verify retains the deploy result and adds `verification`. No observed Berry error is general proof of correctness. Optional `--capture` returns the existing atomic PNG capture metadata. `runtime_success_guaranteed:false` is unconditional.

`logs read [--after N]` performs `GET /api/v1/logs?after=N` (default cursor 0) and returns `{after,next,lines,history_limit:34,exhaustive:false}`. `logs follow [--after N] [--interval-ms N] [--duration-secs N] [--script TEXT]` polls that same route using the last response's `next` as the next `after`. Defaults are 1000 ms and 30 seconds; interval is 1..60000 ms, duration 1..3600 seconds and includes each request (its timeout is clamped to the remaining duration). Follow emits each line immediately on stdout (plain line by default; compact JSONL with `--json`, each record has `type:"log"`, `line`, `cursor`, `complete_history:false`) then an end record identifying the resume cursor, interruption and bounded-history limitation. A poll error after streaming emits typed JSONL `error` and `end` records with the last confirmed resume cursor, then exits nonzero. `--fields` is rejected for follow before any network request; it remains available for read. `--script` is a literal substring filter, not a parsed Berry log format. Ctrl-C ends successfully after any current bounded HTTP request. The server retains only 34 lines, each capped at 120 characters; drops can occur between polls and historical collection is never claimed exhaustive. `describe logs [read|follow]` lists command-specific parameters, schemas and examples.

The official HTTP reference documents `GET /api/v1/logs`, integer `after` defaulting to 0, response `{next,lines}`, and the 34-entry ring buffer. Each official platform OpenAPI (retrieved 2026-10-07) defines the same GET route, integer `after` query parameter, and 200 JSON object with integer `next` and string-array `lines`: [ESP32](https://blueforcer.github.io/awtrix-ng/esp32/api/openapi.yaml), [ESP32-S3](https://blueforcer.github.io/awtrix-ng/esp32-s3/api/openapi.yaml), [TC002](https://blueforcer.github.io/awtrix-ng/tc002/api/openapi.yaml). Reference: https://blueforcer.github.io/awtrix-ng/reference/http.

## Ticket 12: modules and resources

`resources files list [--dir DIR]` uses `GET /api/v1/files?dir=DIR` (default `/ICONS`). `upload FILE [--dir DIR]` uses documented `POST /api/v1/files?dir=DIR`, multipart field `file`; `delete PATH` uses `DELETE /api/v1/files?path=PATH`. In `/ICONS`, local validation requires a case-sensitive lowercase `.gif` with GIF87a/GIF89a magic or `.jpg` with JPEG SOI magic `FF D8 FF`; failure occurs before HTTP. The server remains authoritative for directory-specific formats, payload acceptance and storage limits (including its 413/507 errors); the CLI does not invent a shared limit. Query arguments are URL-encoded. Inline pushed-app icon values are distinct: documented icon IDs (up to 64 characters) or `data:image/gif.Base64,...` / `data:image/jpeg.Base64,...` data URLs; this resource file uploader does not reinterpret JSON inline icon values. The OpenAPI defines no generic file-download route, so `files download PATH --output FILE` fails locally as `UNSUPPORTED` rather than guessing a URL. All three platform OpenAPI files declare these `/api/v1/files` operations and multipart field `file` (checked 2026-10-07).

Berry modules are installed through `PUT /api/v1/apps/script/{name}` as raw source bearing `@module` in the header, not through an invented module endpoint. `resources modules list` filters `GET /api/v1/apps` for `origin:"module"`; `get NAME` reads the documented raw text `GET /api/v1/apps/script/{name}` route; `deploy NAME (--source TEXT | --file PATH)` requires `@module` in the leading source header and uses the documented raw PUT; `delete NAME` uses `DELETE /api/v1/apps/{name}`. The API's module import name may differ via `@module <name>`. Replacement/deletion does not rewrite consumer imports, and deletion can remove stored script state. These modules are never described as rotation apps. HTTP/transport/auth errors use the shared API error contract; file I/O and icon-magic failures are local errors. Server capacity is variant/device state dependent and is not approximated client-side.

## Ticket 13: TOML script projects

`project init PATH [--name NAME]` creates `PATH/awtrix.toml` and `PATH/src/main.be`; initialization validates the generated manifest before returning success. `project validate [--manifest awtrix.toml]` loads the whole local project without device access. The strict TOML schema requires `[project] name, version`; optional `[target] profile` references a personal profile by name only. Repeated `[[scripts]]` entries require `name,file` and either `create=true` (create-only) or `expected_source_file` (the exact original remote source, captured when the project is authored). A deployment never rereads a remote source to manufacture a reference. `[[modules]]` entries require `name,file` and `# @module` header. `[[resources]]` entries require absolute device `path` and relative local `file`. `[[config]]` entries require a `script` declared in the manifest and a relative JSON object `file`. Local paths resolve from the manifest directory; absolute paths are rejected for local source/reference/config paths. All names and all local files/config shapes are validated before target resolution and any remote mutation. The manifest does not contain credentials.

`project deploy [--manifest awtrix.toml] [--force]` runs modules, resources, scripts, then config patches in manifest order. It is additive; undeclared apps/files are not inspected or deleted. Scripts use ticket 07 `scriptUpdates` conditional writes with the stored `expected_source_file` content or create-only null reference. `--force` explicitly uses the weaker unconditional raw PUT for scripts; it is never an automatic fallback. Target selection remains `--target`, `AWTRIX_URL`, command/environment profile, project profile, global default profile; environment/command credentials override profile credentials. JSON success includes `succeeded`, `failed:null`, `not_run:[]`, target origin, `additive:true`, `transactional:false`. On first remote operation error, the CLI stops, exits nonzero, and returns a machine report with `succeeded`, `failed_operation`, `not_run`, `cause`, and `transactional:false`. No rollback across device operations is promised. A successful HTTP mutation does not guarantee later Berry runtime health.

## Ticket 15: Linux headless lifecycle

`awtrix headless start --binary PATH [--port PORT] [--width WIDTH] [--height HEIGHT] [--data DIR] [--webui FILE] [--ready-timeout-secs SECONDS]` launches only the explicitly supplied executable (or `AWTRIX_LINUX_BIN`), with port default 8080, display 52×16, and readiness bound default 15 seconds (range 1–300). The binary receives the official `--data`, `--port`, `--width`, and `--height` flags, and optional official `--webui FILE`. Before starting a process the CLI attempts to bind the requested loopback port; an occupied port fails locally without spawning. Since the port is released immediately before spawning, readiness additionally requires both a successful `GET /api/v1/device` and evidence in `/proc` that the spawned PID owns the listening socket inode for that port. A different service returning HTTP 200 can never establish readiness/ownership. An omitted data path creates a uniquely named temporary isolated directory that is removed by successful `stop`; an explicit data path is persistent and retained. Start JSON identifies `target`, `pid`, `data`, `temporary_data`, and `owned`. `status` and `stop` use the mode-0600 atomic local ownership record (next to the selected AWTRIX config path, or `$HOME/.config/awtrix/headless.json`). Stop opens a Linux pidfd, verifies the recorded `/proc/PID/stat` start-time through that stable process handle, then signals via pidfd; PID reuse between validation and signal cannot redirect the signal. Stop sends SIGTERM and waits up to five seconds; it never escalates to an unverified kill. A startup guard kills/reaps the spawned child and removes only its temporary data on all readiness errors or Ctrl-C. This ownership record is intended for the same trusted user; no cross-user process management or remote process control is promised. The command is Linux-host-only and never downloads the AWTRIX executable. `describe headless` documents that headless does not validate sensors, audio, or physical ESP32 resource budgets. The supplied Linux executable must be built separately following the official [AWTRIX Linux developer guide](https://blueforcer.github.io/awtrix-ng/tc002/developers/linux/).

In an isolated Linux workspace, dependencies were populated with `uv tool run --from platformio pio pkg install -e native`; CMake was supplied transiently with `uv tool run --from cmake cmake` (no system installation). Build commands: `uv tool run --from cmake cmake -S . -B /tmp/opencode/awtrix-ng-build -DCMAKE_BUILD_TYPE=Release` and `uv tool run --from cmake cmake --build /tmp/opencode/awtrix-ng-build --target awtrix-linux --parallel 4`. After adding process-owned listener verification, the rebuilt CLI again started the real binary on `127.0.0.1:18945` with 52×16 dimensions and explicit persistent data. Real `GET /api/v1/device` identified `version:1.2.2`, `boardType:linux`, and `soc:x86_64`; CLI status reported running and CLI stop succeeded while preserving explicit data and removing the ownership record. Occupied-port and port-stealing race tests prove the CLI refuses to claim or stop an external HTTP service. The artifact/build tree is temporary and not bundled or auto-downloaded.
